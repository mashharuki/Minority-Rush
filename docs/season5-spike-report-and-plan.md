# Season 5 方針転換: 試作の分析結果と改修計画

作成日: 2026-11-16 / 対象: Zama Developer Program Season 5 "Confidential Gaming"（締切 2026-12-14 23:59 AOE）

## 1. 結論

- **「1 対 1 インディアンポーカー」は技術的に成立する**。試作（モック FHEVM）で必要な 3 要素がすべて通った。
- 本番ネットワーク（Sepolia）での遅延と実コストは**未検証**。Sepolia での E2E が最初の関門（Go / No-Go）。
- 関門を通らない場合の退避先「誰とも被らない最小の数字」も試作で成立を確認済み。
- 推奨は、インディアンポーカーで進め、第 1 週末に Sepolia E2E で判定すること。

## 2. 背景と判断基準

Season 5 の審査軸は、遊びやすさと UX、秘匿の設計、公平性（検証可能なオンチェーン乱数）、最後まで動くこと、デモ品質、コード品質（重みの記載なし）。公式ページは「FHE が動くのは入場券で、ゴールではない」「面白さを重視する」と述べ、判定の問いは「状態が公開されたらゲームが壊れるか」。

現行の Minority Rush は FHE の必然性は強い（多数の秘密入力の集計）が、ゲームとして面白くない。コイン投げに近く、1 人で試せず、1 日 4 回の時刻にしか動かない。優先順位は「FHE の必然性（秘匿設計）」を最上位とした。

## 3. 試作の内容と結果

使い捨てのコントラクトとテストを書き、モック FHEVM（Hardhat）で実行した（7 テスト成功）。コードは本ブランチの `contracts/spike/`・`test/spike/` に未コミットで残してある（削除は未実施）。

### 3.1 インディアンポーカー（`IndianPokerSpike`）

| 確認項目 | 結果 |
| --- | --- |
| 1〜13 から重複なしで 2 枚をオンチェーン乱数で配る | 成功。60 回配って常に範囲内・重複なし |
| 相手にだけカードを見せる（ACL） | 成功。B は A のカードを復号でき、A は自分のカードを復号できない。第三者はどちらも復号できない |
| 勝敗結果だけを公開し、カードは非公開のまま | 成功。`publicDecrypt` はカードに対して拒否され、勝敗の 1 bit だけ公開された |
| 結果の偽造と再提出の拒否 | 成功。偽の結果は revert、同じ証明の再提出も revert |

HCU（モック計算値。上限は 1 tx あたり合計 20M・直列深さ 5M）:

| 処理 | 合計 HCU | 深さ |
| --- | --- | --- |
| 配札（`deal`） | 約 2.72M | 約 1.40M |
| 勝負（`showdown`） | 約 0.06M | 約 0.06M |

配札の大半は `rem(randEuint64, 13)` のコスト。型を小さくする余地がある（改修計画 P1）。

### 3.2 誰とも被らない最小の数字（`LowestUniqueSpike`、退避先）

数字ごとの暗号化カウンタ（ヒストグラム、K = 8）で集計する方式。

| 確認項目 | 結果 |
| --- | --- |
| 最小の被らない数字を選ぶ | 成功（[2,2,5] → 5） |
| 全員被りなら勝者なし | 成功 |
| 範囲外の入力（0, 9, 200）は無視 | 成功 |
| 各自が自分の勝敗だけ復号 | 成功 |

HCU: `enter` は 1 回あたり約 1.14M（人数に依存せず一定）、`close` は 3 人で 1.29M、10 人で 2.23M、19 人で 3.45M。深さは一定（0.58M）。100 人でも合計 20M を超えない見込み（線形外挿、未測定）。

## 4. 審査軸との対応（実コード確認の範囲）

| 審査軸 | インディアンポーカー | 根拠 |
| --- | --- | --- |
| 秘匿設計 | 強い。「自分のカードを本人も運営も知らない」を ACL で実現 | 試作で確認 |
| FHE の必然性 | 強い。公開なら成立しない。ディーラー不在を 1 コントラクトで実現 | 試作 + 設計 |
| 公平性 | 強い。乱数も配札もオンチェーン、誰も事前に知れない | 試作で確認 |
| 遊びやすさ・UX | 要検証。待ち時間が体験を決める | 未検証 |
| 最後まで動く | Sepolia で未確認 | 未検証 |

## 5. 主なリスク

| リスク | 影響 | 対処 |
| --- | --- | --- |
| Sepolia の遅延（暗号演算と復号の待ち）で体感が悪い | 面白さと UX | 第 1 週末の E2E で実測し、操作ごとの待ち時間を決める。許容外なら退避 |
| 配札が重い（約 2.7M）。ブロック全体の上限に当たる可能性 | 配札の失敗 | 型を小さくする。失敗時は再試行 |
| 1 人で試せない（審査員に相手が必要） | 評価されにくい | ボット席（任意）、または 2 アカウントで操作するデモ手順を README に書く |
| 放置・離脱で卓が止まる | 資金がロックされる | 手番ごとの制限時間と `claimTimeout` |
| 3 人以上は共謀が可能（互いに自分のカードを教え合える） | 公平性 | 1 対 1 に限定し、共謀はスコープ外と明記 |
| 他の応募作と発想が被る | 差別化 | 簡易検索では同種の作品は見つからなかったが、不在の証明にはならない。「負けたブラフは明かされない」を前面に出す |
| 試作はモックのみで、本番との差が残る | 想定外の失敗 | Sepolia で通し確認（P3） |

## 6. ゲーム設計（案。実装前に確定する）

- **1 対 1、1 ハンド制。** カードは 1〜13 の 1 枚。自分のカードは自分に見えず、相手のカードだけ見える。
- **賭け:** アンティ 1 単位を各自が出す。手番ごとに チェック / ベット（1 単位）/ コール / フォールド。ベットと再ベットは各 1 回まで。賭け額は公開（ゲーム状態）。カードは秘匿。
- **勝負:** 両者が降りずに終わったら `FHE.gt` の結果だけを公開。負けたカードは誰にも明かされない。フォールドの場合もカードは明かされない。
- **精算:** チップ（ERC-7984）で、勝敗確定後に公開済みの金額を移す。
- **放置:** 手番ごとの制限時間。超過したら相手が勝利を請求できる。
- 毎日の時刻・ストリーク・シェアグリッドは対象外（ポーカーでは不要）。

## 7. 改修計画

期間は 4 週間（締切は 12/14）。12/12 までに提出できる状態を目標にする。

| 週 | 作業 | 成果物 / 判定 |
| --- | --- | --- |
| 第 1 週（11/16–11/22） | P1 コントラクト `IndianPokerGame`（卓・賭け・タイムアウト・精算）。配札の型を縮小して HCU を下げる。ユニットテスト。P2 Sepolia へデプロイし、実際の遅延と HCU を測る | **Go / No-Go（11/22）**: 1 手あたりの待ち時間と E2E の成否 |
| 第 2 週（11/23–11/29） | Web UI: 卓の作成と参加、相手のカード表示（復号の権限リクエスト）、賭け UI、結果表示。チップ・ガス代不要ログイン・PWA の枠は流用 | 2 アカウントで 1 ハンドが完走する |
| 第 3 週（11/30–12/6） | 磨き込み、ボット席（任意）、Sepolia 通し確認、`fhevm_lint` とセキュリティチェックリスト、テスト拡充 | 品質ゲート通過 |
| 第 4 週（12/7–12/13） | 3 分動画（本人出演）、README とドキュメント、X 投稿、フォーム提出 | 12/12 までに提出 |

### 7.1 流用・置換・削除

- **流用:** `RushChip`（ERC-7984 チップとファセット）、Hardhat 設定、デプロイと ABI 出力のスクリプト、Web の認証・ガス代不要・PWA、`liveClient` の枠組み。
- **置換:** `MinorityRushGame` → `IndianPokerGame`。Web の画面（Home、ラウンド表示）を卓中心に作り直す。
- **削除候補:** 日次スケジュール、ストリーク、シェアグリッド、`settleQueue` のうちラウンド専用の部分（実コードを確認して判断）。

### 7.2 品質ゲート

- 負の経路のテスト（ACL、偽造と再提出、タイムアウト、不正な手番）。
- 配札と各手番の HCU を計測し、合計 20M・深さ 5M を大きく下回ること。
- Sepolia で 1 ハンドの通し確認。
- `fhevm_lint.py` の指摘を解消または根拠を明記。

### 7.3 退避計画

11/22 の判定で次のいずれかに当たれば「誰とも被らない最小の数字」へ切り替える。

- 1 手あたりの待ち時間が長すぎて遊びとして成立しない。
- Sepolia で配札や復号が安定して通らない。

退避先は既存の `MinorityRushGame` の流れ（入場 → 締切 → 確定 → 請求）と試作のヒストグラム方式を使えるため、切り替えのコストは小さい。

## 8. 未検証の事項

- Sepolia での遅延、実コスト、ブロック単位の HCU 上限との相互作用。
- 相手のカードを UI で復号するときの体験（署名リクエスト、待ち時間）。
- 100 人規模の「最小の数字」の HCU（線形外挿のみ）。
- 他の応募作との重複（検索では確認できなかっただけ）。

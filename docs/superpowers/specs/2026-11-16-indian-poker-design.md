# 設計書: 1 対 1 インディアンポーカー（ライブ卓 + ボット必須）

作成日: 2026-11-16 / 状態: 承認待ち / 関連: [試作の分析と改修計画](../../season5-spike-report-and-plan.md)

「決定」はあなたが選んだこと、「私の判断」は私が置いた仮の決めで、修正できる。

## 1. 目的とその理由

Zama Developer Program Season 5「Confidential Gaming」（締切 2026-12-14 23:59 AOE）に応募する。公式の評価は、遊びやすさと UX、秘匿設計、公平性、最後まで動くこと、デモ品質、コード品質。「FHE が動くのは入場券で、ゴールではない」「面白さを重視する」と明記されている。

現行の Minority Rush は FHE の必然性は強いが、コイン投げに近く、1 人で試せず、1 日 4 回しか動かない。そこで、FHE でなければ成立しない隠し情報のゲームに置き換える。

**ゲーム:** 各プレイヤーのカードは**相手にだけ見え、本人には見えない**（インディアンポーカー）。賭けのやり取りでブラフを読み合い、勝負では**勝敗の 1 bit だけ**が公開される。負けたカードは誰にも明かされない。

## 2. ゴール / ノンゴール / アンチゴール

**ゴール**
- 2 人が同時にオンラインで 1 ハンドを 2〜3 分で完走できる（ライブ卓）。
- 審査員が 1 人でも、すぐボットと遊べる。
- 「自分のカードを、本人も運営者も知らない」を、実際に動くコードで示す。人間のカードはボット（相手）には見える。ボット自身のカードは、ボットにもその運営者にも見えない。
- 待ち時間が気にならない体験（§7）。
- 12/12 までに提出できる状態にする。

**ノンゴール（今回やらない）**
- 3 人以上、レイズの応酬、1 卓での連続ハンド、トーナメント。
- 毎日の時刻、ストリーク、シェアグリッド、ランキング。
- メインネット、実価値のあるトークン、監査。
- Web プッシュ通知（タブを開いている間の音・振動・タイトル点滅のみ）。

**アンチゴール（動いても失敗とみなす）**
- FHE が飾りで、サーバーでも作れるように見える。
- 運営者が、ボット自身のカードや、ルール上相手にも見えないはずのカードを見られる（ボットは卓の「相手」なので、人間のカードを復号して見ることは仕様）。
- 待ち時間で「壊れている」と感じさせる。
- 2 人の人間がいないと何も試せない。

## 3. 制約

- 締切は 2026-12-14 23:59 AOE。提出物は、Sepolia 上のコントラクトとフロントエンド、ドキュメント、3 分の動画（本人出演、AI 生成は不可）、X 投稿。
- ネットワークは Ethereum Sepolia。現行の依存は `@fhevm/solidity` 0.11.1、Hardhat 2、`@zama-fhe/sdk`（Web）。Zama の最新版とずれがあるため、Sepolia での動作を第 1 週に実機確認する。
- FHE の上限は 1 tx あたり合計 20M HCU・直列深さ 5M HCU。
- 既存資産を流用する: `RushChip`（ERC-7984 チップとファセット）、デプロイと ABI のスクリプト、Privy ログイン、ガス代スポンサー、PWA。

## 4. アプローチ

| 案 | 内容 | 結果 |
| --- | --- | --- |
| **1 対 1 インディアンポーカー（採用）** | ACL でカードを相手にだけ見せる。勝敗だけ公開 | 試作で成立を確認。秘匿設計が最も強い |
| 誰とも被らない最小の数字（退避先） | 数字のヒストグラムを暗号化して集計 | 試作で成立を確認。必然性は強いが、発想が重なりやすい |
| 隠し盤面を掘る非同期ゲーム | プレイヤーが隠し、他が掘る | 状態が多く、4 週間では重い |
| ディーラー不在のフルポーカー | 暗号化シャッフル、複数人 | 最強だが実装が最も重い |

**待ち方の決定:** ライブ卓（手番 45 秒）を採用し、非同期卓は見送る。理由は、1 ハンドが短く、デモと動画に向くため（決定）。

## 5. ゲームルール（私の判断）

- 1 卓 = 1 ハンド。座席は作成者が A、参加者が B。
- カードは 1〜13 から重複なしで 1 枚ずつ。A のカードは B にだけ見え、B のカードは A にだけ見える。
- **預託:** 参加時に各自が 2 チップをコントラクトに預ける（アンティ 1 + ベット 1 の最大露出）。アンティとベットは**全卓で固定（各 1）**とし、可変にはしない（スコープ削減。私の判断）。
- **手番（Kuhn ポーカー型。レイズなし）:**
  1. A: チェック または ベット（1）。
  2. A がベットなら B: コール または フォールド。
  3. A がチェックなら B: チェック（勝負）または ベット（1）。B がベットなら A: コール または フォールド。
- **決着:** フォールドなら相手の勝ち。コールまたはチェック・チェックなら勝負（`FHE.gt` の結果だけを公開）。
- **精算:** 勝者がポット（預託の使用分）を受け取り、未使用の預託は返る。金額は賭けの記録から決まる公開値。誰が何チップ持っているかは秘匿のまま。
- **放置:** 手番の制限は 45 秒。超過したら誰でも `claimTimeout` を呼べ、手番側の負けになる。
- **相手待ち:** 参加者が来ない卓は、作成者が `cancel` で預託を取り戻す。

## 6. コントラクトの設計（`IndianPokerGame`、`MinorityRushGame` は 11/22 まで残す）

旧 `MinorityRushGame` とそのテスト・既存の UI は、**11/22 の Go / No-Go までは削除せず**に残す（退避先に切り替えられるようにするため。私の判断）。新コントラクトは別ファイルで追加する。UI の置き換えは Go の後に始める（第 2 週）。Go したら旧ゲームと旧画面を削除する。

**状態遷移:** `Open`（相手待ち）→ `Betting`（配札済み、賭け中）→ `Showdown`（結果公開待ち）→ `Settled`。`Cancelled` と `TimedOut` も終端。

**配札:** 2 人目の `join` の tx の中で配札まで行う（待ちの削減）。1〜13 から重複なしで 2 枚。試作の方式は `rem(randEuint64, 13)` と `rem(randEuint64, 12)` に「`b >= a` なら `b + 1`」の補正（HCU 約 2.7M）。型を縮小して下げる（私の判断。ビルダーに任せる）。ACL は、A のカードを B にだけ、B のカードを A にだけ `allow`。コントラクト自身は `allowThis`。

**預託の検証（私の判断）:** ERC-7984 の `confidentialTransferFrom` は残高不足でも revert せず 0 を移す。そこで、参加時に受け取った額が 2 に等しいかを暗号化フラグ `okA`・`okB` として保存し、2 人目の `join` で公開復号の対象にする。復号は**ハンド開始と並行して**行い（プレイ中に裏で完了する）、クライアントが `confirmFunds(証明)` を自動で提出する。`confirmFunds` が済むまで精算（`finalize` / `claimTimeout`）はできない。通常は賭けの途中で済むので、精算の待ちは増えない。
- どちらか（または両方）が不足なら、**そのハンドは無効**にして、各自が払った分だけを返す。勝者は出さない。相手のチップは動かさない。
- フォールドやタイムアウトでも、精算前に `confirmFunds` が必要（条件は同じ）。

**精算（`finalize`）:** 勝負なら、公開復号の証明を `FHE.checkSignatures` で検証して勝敗を確定する。フォールドとタイムアウトは勝敗の復号が不要で、`confirmFunds` 済みなら即精算できる。保存済みのハンドルから組み立て、段階フラグで再提出を防ぐ。精算の送金（`confidentialTransfer`）も同じ tx に含め、`claim` の手順は作らない。

**公開と秘匿:**
- 公開: プレイヤーのアドレス、手番、賭けの記録、タイミング、勝敗、預託が足りていたか。
- 秘匿: 両方のカード、各プレイヤーのチップ残高。

**HCU:** 配札の tx が最大。目標は合計 5M 未満、深さ 2M 未満（上限の 1/4）。テストで測る。

## 7. 待ち時間の設計

| 場面 | 実際の待ち | 対策 |
| --- | --- | --- |
| 参加と配札 | tx 確定と FHE 計算 | `join` の中で配札まで済ませる。待ちはカードを配る演出で見せる |
| 相手のカードの復号 | リレイヤーと KMS の往復 | 配札の検知で即座に復号を開始。復号の署名許可は卓に入るときに 1 回だけ取る |
| 自分の賭け | tx 確定（約 12 秒） | **楽観的 UI**: 押した瞬間にチップが動き「確認中」を表示。Privy の埋め込みウォレットとガス代スポンサーで承認ダイアログなし |
| 相手の手番 | 人間の思考時間 | 手番タイマーの輪、音、タイトル点滅。45 秒で自動的にタイムアウト |
| 勝負と結果公開 | 公開復号 + finalize tx | クライアントが結果提出を自動で行う（どちらのクライアントでも可、2 つ目は無害に失敗）。待ちは「めくり」の演出で隠す |

**予算（私の判断。第 1 週に実測して調整）:** 操作の反応は 1 秒以内、確定は 15 秒以内、勝負の結果公開は 40 秒以内。

## 8. ボット（必須。私の判断）

- **形:** Vercel の関数（`apps/sponsor-api` と同様の構成）。ブラウザが操作の直後に `POST /api/bot/act` を呼んで起こす。常駐サーバーは持たない。取りこぼしに備え、定期実行（cron）も併用する。
- **動作:** 卓を読み、ボットのアカウントで参加し、相手（人間）のカードを SDK で復号して、簡単な確率戦略で賭ける。人間のカードがボット（と鍵を持つ運営者）に見えるのは、相手に見えるというルールどおりで仕様。一方、ボット自身のカードは**ボットにも運営者にも見えない**（人間と同じ立場）。動画や README では、この範囲を正確に説明する（「運営者にもカードが見えない」とは言わない）。
- **濫用対策（私の判断）:** `/api/bot/act` は、`apps/sponsor-api` と同じ Privy トークンの検証と、レート制限を使う。injected ウォレットの利用者向けには、卓の作成者の署名でも認証できる形にする（ビルダーが判断）。1 ユーザーあたりのボット卓は同時 1 つ、全体の同時ボット卓数に上限を置く。ボットの ETH またはチップが下限を下回ったら、新しい卓の受付を止めて画面に表示する。
- **戦略:** 相手のカードが高ければコールを控え、低ければベットやブラフを混ぜる（閾値 + 乱数）。
- **資金:** ボットのアカウントは Sepolia ETH と RUSH チップを持つ。チップは `RushChip` の `faucet`（20 / 日）だけでは足りないため、テストネット専用の管理者用 `mint` を足す案（ビルダーが判断）。ボット卓のアンティは固定 1。
- **鍵:** ボットの秘密鍵は環境変数のみ。ブラウザには出さない。

## 9. Web の変更

- **置換:** Home と Round 画面 → ロビーと卓の画面。
- **ロビー:** 「ボットと対戦」「卓を作る」「招待リンクで参加」「開いている卓」。開いている卓の一覧は、コントラクトに直近 N 卓（例 20）の ID を保持して `view` で読む。イベント検索（`getLogs`）やインデクサーは使わない（公開 RPC の範囲制限を避けるため。私の判断）。
- **初回の導線（私の判断）:** 初めての人は、ファセット → `setOperator` → 卓への参加を、Privy のスマートアカウントで**1 つのバッチ（1 UserOp）**にまとめる。injected ウォレットは別々の tx。ガス代スポンサーの許可リスト（`apps/sponsor-api`）は新コントラクトの関数に合わせて更新する。
- **卓の画面:** 相手のカード（復号後に表示）、自分のカードは裏面、ポット、手番タイマー、4 つの操作ボタン、結果の演出。
- **流用:** 認証、ガス代スポンサー、チップ残高、PWA、`liveClient` の枠組み。
- **オフライン用のデモクライアント:** 新しいゲームに合わせて更新する（優先度は低い。ローカル開発用）。

- テスト: 正常系、ACL（本人は自分のカードを復号できない）、偽造と再提出、タイムアウト、不正な手番、預託不足、`cancel`。HCU の計測。`fhevm_lint.py` の指摘は解消または根拠を明記。
- スケジュール: 第 1 週 コントラクトと Sepolia 実機確認 → 第 2 週 Web → 第 3 週 ボットと磨き込み → 第 4 週 動画・文書・提出（12/12 までに提出）。

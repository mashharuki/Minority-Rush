# 定時ラウンド型 Minority Rush 設計

2026-11-14 / 状態: 承認待ち（コードはまだ書かない）

## 1. 目的と理由

Minority Rush を、一般公開して多くの人が「毎日、何度も遊びたくなる」ゲームにする。

オーナーの言葉では、目指すのは「熱中して何度もプレイしたくなる」ゲームで、手本にしたのはパズドラ、パワプロ、ウマ娘、シンデレラガールズ。友達と盛り上がる形も話題に出たが、中心は繰り返し遊ばれることだと本人が明確にした。

いまのゲームは、陣営を選び、待ち、結果を見るだけの1周で終わる。結果が積み上がらず、人に見せる形もなく、戻ってくる理由もない。

調査（`reports/` の2本）から、次の3点を設計の根拠にする。

- 繰り返される核は、1回の完結が短いこと、結果が目に見えること、人に見せたくなる形であること（Wordle、学マス、ツムツム）。
- FHEが本当に必要なのは、多人数の同時の秘密選択を集計する部分。Minority Rush はそこにあたる。
- 秘匿型オンチェーンゲームの商業的な成功例は、調べた範囲で見つかっていない。FHEを看板にせず、運営も見えない公平さの裏付けとして使う。

この文書は、数ある方向の中から「案A: 定時ラウンド型」を選んだ結果を設計にしたもの。案B（連戦シーズン）と案C（育成キャラ）は、案Aで需要が確かめられてから別途検討する。

## 2. ゴール

1. 1日に数回、決まった締切のラウンドがあり、全員が同じラウンドに同時に参加する。
2. 参加者は、ネタバレのない結果グリッドを共有でき、毎日戻る理由として連続参加日数を見られる。
3. 待ち時間（FHEの復号の往復）が、遊び方の邪魔にならない。画面で待たせず、次に訪れたときに結果が見えている。誰も閉じていなければ、開いた人の画面が締切と確定を進め、その間は「集計中」と表示する（初版は、自動で進める役を置かない。第6.3節）。
4. 初めて来た人が、30秒以内に最初の1手を封印できる（メールログイン、ガス代なし。既に実装済みなので維持する）。
5. 公開版のポイントに、金銭的な価値を持たせない。

## 3. ゴールでないこと

- キャラクター、育成、収集、ガチャ（案B・案C。別の設計とする）。
- 賞金、トークンの換金、価格に連動する報酬。
- メインネットへの展開（第7節の未決事項を参照）。
- プッシュ通知（初版では見送る。PWAのiOS対応を含め、別途検討する）。
- 全体ランキング（初版は個人の統計のみ）。

## 4. 避けたい失敗（アンチゴール）

- ラウンド中に、誰かの陣営や賭け金が漏れること。
- 運営者だけが操作できる仕組みになること（誰でもラウンドを進められる性質を保つ）。
- 人数を水増しするために、偽のプレイヤー（ボット）を入れること。
- 賭博と見なされうる設計になること。
- 数字を大きく見せるために、人為的な活動を作ること。

## 5. 制約

- **待ち時間は未実測。** 復号の往復は「最低3〜4回のチェーン確定」という推定だけで、Sepolia でも本番でも実測していない。設計は、数分かかっても成立するようにする。
- **現在のコントラクトの制限。** `MAX_PLAYERS = 8`、`playerCount` は `uint8`、ラウンドは同時に1つだけ、1人の参加ごとに ERC-7984 の `confidentialTransferFrom` が走る（`packages/contracts/contracts/MinorityRushGame.sol`）。
- **ガス代の負担。** 参加と受け取りのたびに、Pimlico 経由でガスを肩代わりしている。数百人規模ではコストが無視できない。
- **公開される情報と非公開の情報。** アドレス、人数、時刻、勝った陣営は公開される。各人の陣営、賭け金、報酬、残高は非公開（README のとおり）。この区分は変えない。
- Zama の乱数は、トランザクション内でしか生成できない。同点の決着は現状のまま使える。
- プロジェクトのルール（`.claude/rules/`）に従う。UI は `app-ui-design` の規則に沿わせる。

## 6. 方向と実現方法

### 6.1 選んだ方向

案A「定時ラウンド型」。1日に数回の決まった締切で、全員が同じラウンドに参加する。開票後にネタバレのない結果グリッドを共有でき、連続参加日数が出る。

### 6.2 検討した方向

| 案 | 内容 | 採否と理由 |
|---|---|---|
| A 定時ラウンド型 | 1日数回の締切、結果の共有、連続参加 | **採用。** 待ち時間が問題にならず、人が同じ時間帯に集まり、実装が軽く、賭け金なしで規制リスクも最小 |
| B 連戦シーズン型 | 1ラン10ラウンド、連続的中の倍率 | 見送り。常に人が集まっている必要があり、待ち時間も10回分かかる |
| C 育成キャラ型 | 選択の癖を持つキャラを育てる | 見送り。美術と設計のコストが最大で、少数派のコアが面白いかもまだ未検証 |

### 6.3 ラウンドの進め方（実現方法）についての私の判断

ここはオーナーが細かく指定しなかったので、私が決めた。

| 案 | 内容 | 判断 |
|---|---|---|
| 1. 参加者の画面が進行役 | 最初に来た人の画面が、ラウンドの開始・締切・確定を呼ぶ | 一部採用。いまの実装がすでにこの形で、人が誰も来ない時間帯は進まなくてよい |
| 2. 固定の締切をコントラクトに持たせ、誰でも進められる | 締切の時刻を決まった刻みにそろえ、誰でも開始・確定できる | **採用。** 運営者が不要で、誰が進めても同じ結果になる |
| 3. サーバーで定期実行 | サーバーが時刻どおりに実行する | 見送り。運営者の署名キーが必要になり、運営者だけが操作できる仕組みに近づく |

つまり、2を土台にして、1のように参加者の画面が実際に進める。

**自動で進める役（キーパー）は、初版では置かない**（私の判断）。誰も画面を開いていない時間は、ラウンドが進まなくてよい。ただし、特権を持たない鍵で `closeRound` と `finalizeRound` を定期的に呼ぶだけのキーパーは、3の「運営者だけが操作できる仕組み」にはあたらない。結果が出るまでの時間が長いと分かった場合に、後から足してよい。ガスを払うだけの鍵が必要になり、その保管と費用が追加される。

## 7. 設計

### 7.1 ラウンドのスケジュール

- 1日に4回の締切を置く。初期値は日本時間の12:00、18:00、21:00、23:00（昼休み、帰宅、夜、就寝前）。
- 各ラウンドの窓は、締切の90分前から締切までとする。初期値では、10:30〜12:00、16:30〜18:00、19:30〜21:00、21:30〜23:00になり、**窓は重ならず、窓の間に30分以上の空きがある**（前版の「3時間前」は21:00と23:00で重なっていたので取り消す）。
- **同時に開いているラウンドは1つだけ**とする（いまの実装と同じ）。
- **締切後の確定待ち（Closing）は、次のラウンドの開始を止めない**（私の判断。いまの実装は Closing 中は止めるので変更する）。確定が遅れても、結果は変わらない。確定待ちのラウンドが複数あっても、それぞれ独立して確定できる。
- 誰もラウンドを開かなかった枠は、飛ばす。後から開いて遅れて始めることはしない。
- 締切の後は、誰でも `closeRound` と `finalizeRound` を呼べる。
- 締切の時刻は、コントラクトの生成時に決めて変えられない（私の判断。運営者だけが変えられる仕組みにしないため）。変えたいときは、新しく配り直す。

### 7.2 コントラクトの変更（概要）

- 参加人数の上限を8から引き上げる。初期値は100人（私の判断。ガス代の予算の上限と、1ブロックあたりのHCUの上限で決める。実測してから調整する）。`playerCount` を `uint16` に広げる。
- 最低人数を2から3に上げる（私の判断。2人だと読み合いにならず、確率で決まりやすいため）。最低人数に届かなければ、いまと同じく中止して賭け金を返す。
- 締切を、決まった時刻にそろえる仕組みを追加する。いまは `roundDuration` が固定の長さ（生成時の引数）なので、これを締切の一覧に置き換え、`startRound` も、「次の枠の窓の中」であることを確かめて開く形に変える。仕組みの詳細は実装担当に任せる。
- `startRound` が止まる条件を、「最新のラウンドが Open のとき」だけにする（Closing では止めない）。
- **すでに配られているコントラクトは、新しく配り直す**（私の判断）。窓の長さが生成時に決まる値で、変更にあたり配り直しが避けられないため。ポイントには金銭的な価値がなく、以前の履歴と残高は引き継がない。sponsor-api の許可リストと、画面が参照するアドレスと ABI も更新する。
- 他は変えない。同点の決着（`FHE.randEbool`）、賭け金の範囲（1〜10）、受け取りの仕組みはそのまま使う。

### 7.3 連続参加日数

- 定義: 1日に1回以上参加した日が連続している日数。日付の切り替えは日本時間の0:00。
- 参加したかどうかは公開情報（アドレスと参加は公開）。コントラクトの `getEntry(roundId, player)` と `getRound(roundId)` の読み取りで分かる。そのため、**コントラクトに新しい状態やイベントを足さず、ラウンドの番号の範囲をまとめて読んで（multicall）画面側で計算できる**（私の判断）。イベントの履歴（`getLogs`）には頼らない。公開のRPCに範囲の制限があるためで、追跡用のサーバー（インデクサー）も置かない。
- 1週間分でも、1日4回なら28ラウンド分の読み取りで済む。
- 1週間に1回、救済用の「凍結」を1つ付与する。1日参加を逃しても、凍結を使えば連続が切れない。凍結の付与と消費は、初版では画面側の計算にとどめる。
- 勝敗は連続日数の条件にしない。勝敗は非公開なので、公開イベントだけで計算できる条件にしたい。

### 7.4 結果の共有

- 1日4ラウンドの結果を、色マスで1行に並べる。
  ```
  Minority Rush #128  連続 6日
  🟩⬛🟩⬜   読み勝ち 2/3
  ```
  🟩は読み勝ち、⬛は外れ、⬜は不参加。陣営と賭け金は載せない（ネタバレを避ける）。
- **勝敗の求め方**: 参加時に、自分の選択を自分だけが復号できるよう許可されている（コントラクトの `FHE.allow(choice, msg.sender)`）。そのため、自分の選択を復号し、公開された勝った陣営（`moonWon`）と画面側で比べて、🟩か⬛かを決める。**受け取り（`claim`）を先に済ませる必要はない**。復号の署名は、画面を開いたときに1回で複数ラウンド分をまとめて済ませる（Zama SDK の許可の仕組み。実装担当が確認する）。
- 中止したラウンドと不参加は⬜にする。「読み勝ち X/Y」の Y は、**参加して中止にならなかったラウンドの数**とする。
- 番号の「#128」は、公開開始日から数えた日数とする（Wordle と同じ。私の判断）。
- 自分の結果の確認は、いままでどおり自分だけが復号できる範囲に限る。共有するかどうかは本人が決める。
- 共有の手段は、Web Share API を第一にし、使えなければテキストのコピーにする。

### 7.5 画面

- ホーム: 次の締切までのカウントダウン、いま参加している人数（公開情報）、参加ボタン、前回までの結果。
- 参加: いまの封印の画面を引き継ぐ（陣営の選択、賭け金、ボタン）。
- 結果: 自分の勝敗、少数派だった陣営、共有ボタン。結果が出るのを画面で待たせず、確定したら次に訪れたときに見えるようにする。
- 連続日数と、直近の結果の色マスをホームに表示する。

### 7.6 待ち時間への対応

- ラウンドの窓が数時間単位なので、復号の往復が数分かかっても影響しない。
- 開票は、締切の直後に起きる。人が画面を開いているときは、少しの演出（カウントダウン、分布の傾き）を見せる。いないときは、次に開いたときに結果を出す。
- **最初に、Sepolia で `closeRound` から `finalizeRound` までの実際の秒数を測る**（小さな試作として、使い捨ててよい）。

### 7.7 ポイントと参加権

- 既存の RushChip の蛇口（faucet）は、いまは**1時間に1回、20チップ**を配る作りで、画面は最初の1回しか呼んでいない。公開版では、**1日1回**にする。待ち時間（クールダウン）は、チップの配り直しの際に24時間へ変える（第7.2節の新しい配り直しに含める）。
- ポイントの残高が足りないとき、`enter` は賭け金0で参加として数えてしまう。画面側で、残高が1に満たなければ参加できない形にする（先に蛇口を促す）。コントラクトは変えない。残高0での参加が最低人数に数えられるすり抜けは、初版では許容する（私の判断。公開してから様子を見る）。
- ポイントは、金銭的な価値を持たせない。換金、取引、価格との連動は作らない。

### 7.8 人が集まらないとき（立ち上げの問題）

- 少数派ゲームは、一定数の人が同じ時間に集まらないと成立しない。人が少ない序盤は、ラウンドが中止になる。
- 対策: 窓を4回に絞って人を集中させる。ホームに「あと◯人で成立」を表示する。招待リンクでの共有を促す。偽のプレイヤーは入れない（アンチゴール）。
- 中止したラウンドは、賭け金を返し、連続日数にもそのまま数える（参加はしたので）。

### 7.9 ガス代の負担

- 参加人数の上限（初期値100人）で、1ラウンドあたりの費用に上限を設ける。
- sponsor-api のレート制限は、メモリ上で、インスタンスごとの、できる範囲での制限にすぎない（`apps/sponsor-api/src/rateLimit.ts` の注記）。**費用の強い上限は、Pimlico の支払いポリシー側で設定する**。1日あたりの予算の警報も、そちらで決める。数字は、実測のあとに決める。

### 7.10 計測する数字

- 翌日に戻ってきた人の割合、7日後に戻ってきた人の割合。
- 1人が1日に参加するラウンド数。
- 共有ボタンが押された割合。
- ラウンドが中止になった割合。
- 締切から結果が確定するまでの時間。

## 8. 受け入れ条件

1. 1日4回の締切で、ラウンドが自動的に開き、閉じ、確定できる。誰が進めても同じ結果になる。
2. 3人以上が参加したラウンドで、陣営と賭け金が結果の確定まで誰にも見えない（既存のテストを維持する）。
3. 3人未満のラウンドは中止になり、賭け金が返る。
4. 参加者が100人のラウンドで、ブロックのHCUの上限に収まる（実測で確認する）。
5. 連続日数と結果グリッドが、イベントの履歴から正しく計算できる。
6. 共有されるテキストに、陣営や賭け金が含まれない。
7. 初めて来た人が、30秒以内に最初の1手を封印できる（現状を維持する）。

## 9. 実装担当に任せること

- 締切を決まった刻みにそろえる具体的な仕組み。
- 参加人数の上限の最終値と、HCUの実測に基づく調整。
- 連続日数の計算の置き場所（画面側か、小さな補助関数か）。
- テストの具体的な項目と、既存の14件のテストの更新。
- sponsor-api のレート制限の値。

## 9.5 実装担当への前提（レビューで確定した私の判断）

読み手役のレビューで挙がった疑問に、次のように答えた。

| 疑問 | 答え |
|---|---|
| ラウンドは重なってよいか | 重ならない。窓は90分で、間に30分以上の空きを置く。Closing は次の開始を止めない |
| 誰もいないとき、誰が締切と確定を進めるか | 初版は、開いた人の画面が進める（「集計中」と表示）。特権のないキーパーは後から足してよい |
| 勝敗を画面はどう知るか | 自分の選択を復号して、公開された勝った陣営と比べる。受け取りは不要 |
| 蛇口を1日1回にするには | チップを配り直し、クールダウンを24時間にする |
| 配り直しで以前の履歴が消える | 許容する。ポイントに価値はない |
| イベントの履歴はどこから | 読み取り関数の複数ラウンド分のまとめ読み。インデクサーは置かない |
| 締切の時刻を誰が変えられるか | 誰も変えられない。生成時に決め、変えるなら配り直す |

## 10. 未決事項（オーナーの判断が要る）

1. **公開するネットワーク。** 公開版は、金銭的な価値のないポイントなので、Sepolia（テストネット）のまま公開するのが最も安全（私の提案）。メインネットに出すかどうかは、法務確認の後に別途決める。
2. **ガス代の予算。** 肩代わりするガスの1日あたりの上限額。上限に達したときの動作（参加を止める、画面に表示する）も含めて決める。
3. **締切の時刻。** 初期値は 12:00 / 18:00 / 21:00 / 23:00（日本時間）。変えたい時間帯があれば指定する。

## 11. 残っている調査の穴

- 復号の往復の実測値（第7.6節の試作で測る）。
- 同時に数百人が参加したときの、実際のHCUとガス代。
- 遊ぶ人が実際に何回戻ってくるか（公開して計測するまでは不明）。
- 少数派を主ルールにしたヒット作の前例がないこと。「形式として面白いが続かない」可能性は排除できない。
